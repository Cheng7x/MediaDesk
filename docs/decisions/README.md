# 设计决策记录（ADR）

ADR 保存重要选择为什么成立、何时应重开；现行行为以相应规范为准。目录里只创建真实发生的决策，不预建一整套尚未实施的架构成果。

## 何时记录

影响数据正确性、授权、恢复、模块边界、重要依赖、成本或当前产品承诺的选择，写一份短 ADR。以下情况通常需要：上传跨系统一致性、任务租约/取消、分享撤销语义、引入 MQ/Redis/ES、改变认证或存储方式。

命名、局部函数拆分、普通样式与可逆小修复，用一句理由和适当检查即可。ADR 不等于审批；既有授权内的选择可以直接作出并记录。扩大范围、费用、公开承诺或涉及不可逆后果时，先准备可审阅方案，再请求所需确认。

## 最小模板

```markdown
# ADR-编号：具体决策标题

日期：YYYY-MM-DD
状态：提议 / 待验证 / 已采用 / 已拒绝 / 被 ADR-xxxx 替代

## 问题、事实与约束
要改变的可观察结果；已有代码/测试/资料；时间、资源与兼容边界。
关键未知、假设与置信度，不把推断写成已验证事实。

## 必要条件与候选
最小充分方案；最强替代方案，以及它在哪些条件下更好。

## 主要失败模式
列最重要的输入/边界、部分失败、并发/重复、恢复/观察风险；
按影响、可能性和可检测性选择最便宜的有效检查。

## 决定与边界
做 / 暂缓 / 拒绝 / 先验证，理由、最小范围、明确不做的部分。

## 证据与重开条件
通过门槛、实际验证链接（尚无则明示）、剩余风险、回退方式、重开触发器。
```

改变已采用决定时，新记录说明取代关系，同时更新 PRODUCT / ARCHITECTURE / DEVELOPMENT / QUALITY 的相应契约与 HANDOFF；旧记录保留历史理由。不能只改 ADR 而让实际规范互相冲突。
