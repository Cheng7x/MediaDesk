# ADR-0001：以交付、可靠性和学习证据约束 AI 开发

日期：2026-10-18
状态：已采用，项目文档基线；不代表工程实现或用户能力验收完成。

## 1. 问题与事实

用户需要一套可持续使用的 AI 开发约束，同时满足：有限范围的媒体审阅产品、Java 后端深度、能够解释的个人成果。当前需要决定的是规则组织与开发原则，不是开始实现整个项目。

已知事实：

- 本次写入前项目目录为空，不是 Git 仓库，无应用代码或运行证据。
- 用户提供《MediaDesk 项目规划与实施安排》v1.0，日期 2026-10-18；规划已选择 MediaDesk，分 M0–M7，ES 与 AI 后置。
- 已读取学习协作长期准则与学习总览。后者保留旧 TaskFlow 主线和较旧进度，新 MediaDesk 规划明确取代该项目安排；保留学习原则，不继承过时阶段。
- TaskFlow 的基础与部署实践是规划记载的已有证据，本轮未重跑，不据此推断独立熟练程度。
- 定稿复核时规划的 SHA-256 为 `91841DF45242478F00522FDC078740F0CCBB307491256F09D1F49E62016FA220`。本轮期间来源仅增加主标题并统一换行，归一化后与初读校验值完全一致，正文未变；本轮未修改笔记库。

关键假设：约 10h/项目周仅为容量起点，置信度中，需实际投入校准；可找到成本可控的 S3 兼容实现，当前未验证；文档能减少 AI 偏离但不能替代权限隔离和测试，不能保证任何模型绝不违约。

继承候选是规划中的技术清单。它们是分阶段手段，不能作为“越早全部接入越好”的依据。

## 2. 从必要条件推导

去掉技术名后，目标成立需要：

1. **可用的工作流**：两名用户可以走完一条审阅到交付的流程，失败有反馈。
2. **可信的状态**：权限、版本、配额与任务在重复、竞争、崩溃时不失真，能够恢复。
3. **可解释的能力**：用户获得关键设计与修改机会，成果能对应真实实现、实验与个人工作。
4. **可接续的工作方式**：新对话能区分长期约束和当前事实，知道唯一下一步，不依赖完整聊天记忆。

因此最小方案是：一个 AGENTS 入口、一个短 HANDOFF、五份按职责划分的规范、按需 ADR；只建立文档与基本文件规则，不提前创建应用目录、依赖或空测试。

不变量先于组件：状态的依据、合法转换、授权边界和失败出口先明确，技术按问题与阶段加入。既不因简历关键词提前引入组件，也不以“最小”删掉已确认的核心产品流程。

## 3. 最强替代方案

**将完整规划直接塞进一个 AGENTS 文件。** 优点是只维护一个入口，无链接和分文件成本；短小且阶段很少的项目中更合适。本项目跨八阶段，包含稳定规则、持续变化的命令与进度，整份重复加载和修改更容易混淆计划与事实，因此采用短入口加任务路由。

**让 AI 一次生成整个项目，再由用户学习。** 原型时间紧、学习不构成目标时可能更优；但会压缩本项目核心设计与排错机会。默认给用户核心实践空间，同时保留明确“直接实现”授权，让交付需求不被教学仪式阻塞。

## 4. 预演失败与检查

| 失败模式 | 影响 / 可能性 / 可检测性 | 最便宜的有效检查与措施 |
| --- | --- | --- |
| AI 按完整路线抢跑，用户没有机会参与关键设计 | 高 / 中 / 通常发现偏晚 | HANDOFF 单一接续点、任务范围、意图分工；检查一次“直接实现”和一次“只给提示”是否都能正确落地 |
| 多份文档重复维护进度、命令和规则，逐渐互相冲突 | 中高 / 高 / 中 | 每种事实有唯一位置，其他位置链接；修改时检查引用、阶段与状态口径 |
| 文档看似完备，被误写成系统已完成或用户已掌握 | 高 / 中 / 若无证据则难发现 | 明示工程为空、版本/命令未验证；关键结果必须有测试或实验指针，学习单独表述 |
| 规则太多，普通任务要过重审批和长文档，拖慢实际开发 | 中 / 中 / 易检测 | 只读相关规范；低风险改动走最小检查；仅重要取舍写 ADR，常规可逆选择直接做 |
| 上传/任务表面成功，跨系统部分失败或越权未验证 | 高 / 中 / 演示难发现 | 预定义 T01–T11；按阶段做真实依赖、竞争与崩溃实验，未验证不宣称可靠 |

前三项优先在本轮文档中检查；最后一项在真实实现阶段验证，不能用文档审阅冒充故障通过。

## 5. 决定与行动边界

采用本套文档组织和分阶段工作方式。现行规范的唯一职责为：PRODUCT 管产品/阶段，ARCHITECTURE 管不变量，DEVELOPMENT 管编码/契约/环境/命令，QUALITY 管验收，LEARNING 管分工；HANDOFF 管实际状态。

本次增加的保守默认明确写入产品和开发契约：Owner 独占交付分享与删除/恢复；唯一 Owner 不可意外移除；不可见资源统一 404、可见但操作无权用 403；签名期限不超过分享剩余期限。这些是可审查的设计选择，不是假称用户原文已逐项指定，也不是运行验证结果。后续真实需求可触发调整。

原规划“Java/Boot 只调整一次”的意图落实为避免反复重选版本，而不阻止有新安全或兼容证据时的必要升级。每次这种调整说明触发原因、影响并重新验证，避免把次数限制变成长期维护障碍。

本轮只创建 Markdown、`.editorconfig` 与 `.gitignore`。不初始化应用、Git 或远端，不启动容器、不安装依赖、不执行付费调用或公网发布；该边界来自用户本次文档请求和当前实际状态。

文档规则由 AI 在上下文中遵守，文件设置由支持它们的工具执行。真正的工程防线还需要在后续阶段建立数据库约束、服务端权限、隔离环境与 CI，不把本轮文档称为自动化安全门禁。

## 6. 证据门槛、风险与重开

本轮门槛：文件为有效 UTF-8，内部文件链接可解析；M0–M7 和 T01–T12 不缺项；预算与源规划一致；规范无互相冲突的默认行为；没有将代码、环境、测试、性能或用户掌握写成既成事实。完成记录见 HANDOFF。

工程机制参考在 2026-10-18 核对了 [S3 multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)、[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)、[Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。这些支持机制边界，不证明尚未选择的 S3 兼容实现和版本组合可用；实施时必须按锁定版本重验。

剩余风险：规则可能被忽略；文档会随代码演进失效；时间和存储兼容性仍未知。以真实失败、频繁重复阅读成本或实际资源限制为依据调整，不能因为新框架热度改路线。

重开触发器：学习目标/协作模式改变、出现新用户或角色需求、资源/预算限制改变、M2/M4 真实耗时显著偏离、现有模块边界阻碍交付，或规则造成持续重复工作。改动局限于受影响规范；此治理方案可通过合并/调整文档回退，不需要预先重构业务实现。
