# 质量、完成定义与证据

验收用于发现最重要的错误并支持接续，不以测试数量、文档长度或仪式多少评价成果。规则随功能引入阶段生效，不要求 M1 提前通过 M7 的实验。

## 1. 一次任务的完成定义

满足当前任务全部适用项才可称为完成：

1. 授权范围内的可观察行为已经实现，成功路径与必要的失败反馈可用，没有隐藏的占位返回或假成功。
2. 对应的产品规则、权限与数据不变量成立；新状态、接口或配置有明确契约。
3. 运行与改动风险相称的验证，结果可追溯；失败、跳过和未覆盖范围如实说明。
4. 涉及状态或使用方式变化时同步规范、运行说明和 HANDOFF，留下一个接续点。

纯说明问题无需改文件；纯文档检查 UTF-8、链接与一致性；低风险样式检查相关页面即可。不要为简单可逆修改写只复刻实现的测试。

## 2. 怎样选择验证

| 变化 | 最小有效验证 |
| --- | --- |
| 状态规则、参数转换 | 针对边界和非法转换的单元测试 |
| 资源鉴权、嵌套 ID、角色变化 | API 越权与撤销测试，包含实际资源关系 |
| SQL、约束、迁移、事务、竞争 | 真实 MySQL/Testcontainers；同时验证失败回滚与条件更新 |
| 对象存储、上传恢复、签名/CORS | 所选真实兼容实现 + 小样例；检查对象与业务状态 |
| MQ、租约、取消和恢复 | 真实依赖/worker 故障实验，检查最终状态与副作用 |
| FFmpeg 进程与资源限制 | 受控媒体、损坏输入、超时、中断和清理实验 |
| 页面流程、上传状态 | 浏览器保留核心成功链路与恢复链路，检查错误与权限反馈 |
| 缓存/查询优化 | 同一环境、数据和负载下的前后基线 |

关键规则优先自动回归；难以稳定自动化的进程/网络故障可以脚本化实验并保留证据。mock 用于局部隔离，不能证明真实事务、存储兼容或消息恢复成立。

修复缺陷时优先建立能重现该缺陷的有效验证；不能为了“全绿”移除断言、无限重试测试或把关键失败标为忽略。必要检查通过后，除非有新改动或疑点，不重复扩大测试。

## 3. 核心验证矩阵

本表是必须形成的证据目标。当前 T01–T12 全部**未执行**；后续状态只在实际验证后通过报告链接维护，不通过文档勾选推断成功。

| 编号 | 阶段 | 场景与必须检查的结果 |
| --- | --- | --- |
| T01 | M1 起持续 | A 读取/修改其他空间素材、版本、评论、任务或签名被拒绝；混合嵌套 ID、移除成员、SSE/搜索同样不能泄漏 |
| T02 | M2 | 分片断网、刷新后重新选文件、重传；成功分片可复用，内容校验成立，不多建版本 |
| T03 | M2 | 并发完成同一上传与争抢剩余配额；同一结果、结算一次、总量不超额 |
| T04 | M2 | 存储完成后数据库更新失败；核对可恢复，或留下明确可处理失败，不能孤立占用或误删 |
| T05 | M4 | Outbox 发布失败、确认丢失、重复与无路由消息；能补发和检测异常，不重复发布最终业务结果 |
| T06 | M4 | 运行中退出、媒体完成而写回前退出；满足恢复条件后重调度，旧 token 不得发布最终结果 |
| T07 | M4 | 取消、完成、心跳、恢复竞争；只有合法状态转换，停止进程，清理无引用输出，双 worker 不普通重复认领 |
| T08 | M3 起 | 损坏文件、超时、临时磁盘不足；有限重试/失败，资源回收，页面可解释 |
| T09 | M5 | 上传新版与提交/完成审核竞争；目标版本明确，冲突可见，旧记录保留 |
| T10 | M5 | 分享撤销、到期及已签 URL；新签名被拒绝，旧签名剩余窗口符合配置与说明 |
| T11 | 各依赖引入时 | MySQL、MQ、Redis 暂不可用；无假成功，拒绝/降级与恢复策略符合契约 |
| T12 | v1.1 | 索引乱序、删除、重建和成员权限变化；旧事件不覆盖新状态，正文/摘要/聚合不泄漏 |

另按阶段检查会话登录/退出、写请求 CSRF、密码字段不暴露、私有对象默认拒绝、分页上限、签名不入日志、迁移可复现。这些是上线前的必要边界，不因没有独立 T 编号而省略。

## 4. 实验记录与性能口径

实验到需要时在 `docs/experiments/` 创建记录，无需现在创建空目录或每日报告。每次重要实验保留以下最小信息：

```text
日期 / 关联任务或 T 编号：
代码版本或可定位的改动范围：
环境、依赖版本、实例数与样本（含文件大小/规格）：
操作 / 可重复命令 / 故障注入点：
预期不变量：
实际状态、日志/指标/输出路径：
通过、失败、未验证部分：
结论、剩余风险与复现/清理方式：
```

只有确实运行后才能填实际结果。已有报告、本次重跑、用户自述和推断分别注明；测试脚本存在不等于测试通过。证据脱敏，可用短日志摘录和生成样例，避免提交大体积原始媒体。

性能先基线、后目标与优化：

- API：并发、样本数、错误率、p50/p95/p99；签名接口响应与实际文件传输分开统计。
- 上传：样例/分片大小、并发、吞吐与重传，说明网络和本机磁盘影响。
- worker：媒体规格、时长、并发、CPU/内存/临时磁盘、排队与处理完成时间。
- 恢复：注入、发现、恢复开始与结束时刻，包含租约等待，不隐藏固定延迟。
- 缓存：同数据/负载下的数据库访问次数、延迟、命中率和错误率；无改善也保留结果。

报告硬件、数据库位置、容器限制、依赖版本、预热、持续时间和重复轮次。小样本 p99 不能代表稳定生产结论；合成负载不称真实用户规模；没有前后对照不写“提升百分之多少”。

## 5. 阶段交付与最终停止线

进入下一阶段：对应 PRODUCT 退出条件有证据，关键失败尚未解决时不默认通过。允许保存部分成果并暂停；未完成项明确保留，不产生补进度债。

v1.0 需要：

- 从新环境复现构建、迁移、运行与配置，CI 完成适用检查；外部发布不由 CI 自动触发。
- 两名测试用户演示上传、批注、新版、审核与固定版本交付，页面失败路径可恢复。
- T01–T11 中适用核心场景有真实证据；T12 留待 v1.1。
- 基础指标和日志能解释至少一次注入故障，关注队列最老等待年龄、Outbox 积压、任务状态/耗时/失败类别、worker 活动、临时磁盘、JVM 和数据库连接池。
- 有一份带环境与边界的性能基线、一轮数据库/对象文件恢复演练、一段核心流程和一段故障恢复演示。
- 有三至四份真实核心实现 ADR：上传一致性、异步恢复、权限/审核，以及缓存或查询选择。本次治理 ADR 不替代这些实现证据。
- README 写清实际能力、启动、限制、出处；简历只写实际完成且能解释的三至四项贡献。

“实现完成”“运行验证通过”“用户能够独立解释”分别表述。设计解释的缺口可成为后续定点实验，不据此否认已有工程结果，也不以一次口头问答判定全部能力。
